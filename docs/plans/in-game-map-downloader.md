# In-game map downloader and landing picker

Status: **done** (phases 0-5 in #520, phase 6 in #537). Tracking issue: [#515](https://github.com/SuperQuentin/UnitSportSwitzerland/issues/515).

Bring `tools/MapSetup` into the game: a "Map" entry on the main menu that shows which parts of
Switzerland are downloaded, lets you search, draw and select what to add, downloads it in the
background while you play, and doubles as the screen you pick your landing zone on when a world
starts.

## Goal

Today real terrain is a developer errand: clone the repo, install Python, GDAL and two .NET SDKs,
run `dotnet run --project tools/MapSetup`, pick tiles on a terminal map. Someone who downloads a
release gets generated terrain and no way forward. After this plan, the game itself is the way you
get Switzerland, and the map is always the thing you look at to know what you have.

## The dependency question, answered

The pipeline MapSetup drives needs Python, the .NET SDK and GDAL. Each was checked against what it
is actually used for:

| Dependency | Used for | Can it be dropped? |
|---|---|---|
| **Python** | `tools/swiss_data.py` — downloads from the swisstopo STAC API | **Yes, dropped.** `swiss_data.py` is standard library only: HTTPS, JSON, SHA-256, zip. Re-implemented in C# it is ordinary `HttpClient` work (phase 1). Nothing to package. |
| **.NET SDK** | building `TerrainPreprocessor` (net9) and `RoadGen` (net8) | **Yes, dropped.** No net9-only API appears in either project, so the preprocessor retargets to net8 and the game references it directly — tiles are built in-process, with no subprocess and no SDK (phase 2). This is also what makes "keep downloading while you play" natural. |
| **GDAL** | `export_buildings.py` and `export_route_keys.py` only | **Eliminated too (#537).** Was not sanely packageable: GDAL + its Python bindings is 150–250 MB per platform, three platforms, with macOS codesigning on top. But it is only used to read **Esri FileGDB** — building TIN solids, and a route-id attribute table — and write GeoPackage. Phase 6 replaced it with a C# FileGDB reader, so nothing in the pipeline needs GDAL any more. |

So after phases 1–2, with **zero external dependencies**, the game can download and build:
terrain, roads, railways, watercourses, land cover, trees, cadastre (GWR) and the place index —
swissTLM3D is a GeoPackage the preprocessor already reads in pure C# (`GeoPackageReader.cs`), and
the TLM and GWR "unpack" steps are plain zip extraction.

**Buildings and cycle routes** are the two layers that still want GDAL in v1. They are not silently
missing: the map screen carries a Requirements panel that names them, says why, and gives the
install line for this platform — and phase 6 removes even that.

## Decisions (agreed)

| Question | Decision |
|---|---|
| Dependencies | Package what can be packaged (Python and the SDK are **eliminated**, not bundled). For GDAL, warn in-game with clear per-platform setup instructions. **This feature is not dev-only.** |
| Devices | Keyboard + mouse + gamepad in v1; VR shows the screen but the map is not pointable yet, follow-up issue. A deferred row still goes in `xr/vr-action-map`. |
| When downloads run | **In the background, while you play.** Tiles appear as they finish; the chunk streamer takes them over from the generated fill. |
| Landing zone | **The map is shown when launching or joining a world**, to choose where to land. Default: the last place you landed, else Riddes. A server-defined default is a follow-up issue. |
| Code sharing | The selection, country map, local scan, plan and estimates move to a shared net8 library both the game and the terminal tool use. No copy. |
| Map look | Real shaded relief from the embedded `swiss_relief.gz`, with lakes, canton borders and place labels — not the terminal version's flat colour blocks. |

## Architecture

### `tools/MapCore` — the shared library (new)

A net8 class library, `UnitSport.Map`, referenced by **both** `UnitSportSwitzerland.csproj` and
`tools/MapSetup`. Everything that is not a user interface moves here out of `tools/MapSetup`:

- `CountryData`, `Town`, `Canton`, `BuildingSheet` — the baked country map.
- `Selection` — the picked tile set (rectangle, disc, canton, bounds, centre).
- `LocalState` — what is already on this machine, read from the files themselves.
- `Paths`, `SetupState`, `Stats` — locations, resume state, measured machine rates.
- `Planner` / `Step` — the ordered steps with their download, disk and time estimates and their
  skip reasons. This is what both front-ends render as a table.
- `SwissDownload` (phase 1) and the in-process stage calls (phase 2).

`switzerland.bin` (425 KB, already gzipped) becomes an **`EmbeddedResource` of MapCore**, the same
trick `swiss_relief.gz` uses, so the game reads the country map with no export-filter or data-path
question. `tools/MapSetup` keeps reading the loose file when `--bake` has just rewritten it.

After the move, `tools/MapSetup` is only its terminal UI (`MapView`, `Program`, `Bake`) on top of
MapCore — the terminal tool keeps every flag it has today.

### What runs the work

`Step.Run` today is `Func<StepRun, Task<bool>>` where `StepRun` starts a subprocess. After phase 2
there are no subprocesses: a step calls into `TerrainPreprocessor` / `RoadGen` as libraries and
reports progress through a callback. One implementation, used by the terminal tool and the game
alike — the terminal tool stops needing `dotnet build` as its first step.

### `src/Ui/MapScreen.cs` and `src/Ui/MapCanvas.cs` (new)

`MapScreen : Screen` is an ordinary page on the `GameShell` stack (`ui/screens`), themed through
`UiTheme`/`UiKit` like every other page. It serves **two roles** from the same code:

- **Library** — reached from the main menu. Selection, estimates, start/cancel a download.
- **Landing** — shown when a world launches or a server is joined. The same map, plus a landing
  marker you move and confirm; selection and download stay available, so "there is no terrain where
  I am about to land" is answered on the spot rather than reported after the fact.

`MapCanvas : Control` draws the map in three cached layers, rebuilt only on change — never per
frame (`general/perf-no-per-frame-allocations`):

1. **Relief**, an `ImageTexture` built on a worker from `ProceduralWorld.Relief`'s 500 m nodes:
   hillshade from the north-west, an elevation ramp, lakes flat, everything outside
   `CountryData.Covered` dimmed to the void colour. Cached per zoom level.
2. **Status**, a second `ImageTexture` at one pixel per km: downloaded, built, selected, queued,
   downloading now. Rebuilt when `Selection.Version` or the job's tile set changes.
3. **Vectors and labels**, drawn in `_Draw`: canton borders (computed once from `CantonAt` edges),
   place labels decluttered by zoom and rank, the landing marker, the cursor and the rubber band.

### Interaction

| | Pan | Zoom | Select | Rectangle | Erase | Search |
|---|---|---|---|---|---|---|
| **Mouse** | right-drag, or middle-drag | wheel, at the cursor | left-drag paints | left-drag, from a click | Shift + drag | the search box |
| **Keyboard** | arrows / WASD | `+` `-` | Enter toggles | `R` anchors, `R` again closes | Shift + Enter | `/` |
| **Gamepad** | left stick | triggers, or LB/RB in steps | A paints | X anchors | B + A | Y, on-screen keyboard |

Every binding is shown through `InputHints` and listed in the controls screen.
`general/new-action-three-devices` asks for the VR answer up front: **the screen renders on the
`XrPad` panel, the map itself is not pointable in v1** — a deferred row goes in `xr/vr-action-map`
pointing at the VR follow-up, and the panel says so rather than leaving a dead map.

### Background downloads

`src/Terrain/Download/DownloadJob.cs`, owned by `GameShell` so it outlives any world:

- Runs MapCore's steps on a background `Task` with a `CancellationToken`.
- Publishes progress as a plain struct the UI polls at a low rate (no per-frame allocation, no
  signal storm).
- Cancelling keeps every finished tile and stays resumable — the existing `mapsetup.json` state
  file already does exactly this.
- Survives entering and leaving a world; the pause menu gets a one-line progress row.

**Live tile arrival** is the one genuinely new runtime behaviour: as tiles are written,
`manifest.json` changes and `ChunkManager` must pick up tiles that were generated fill a moment ago
and are now real. That is its own phase and its own note, because the surrounding generated ground
has to be re-blended at the new boundary (`terrain/generated-fill`).

### Launch flow

`WorldLaunch` gains a nullable landing (`LandingE`, `LandingN`). `SpawnPoint` already takes a target
and already parses `--at`, so nothing downstream changes. `GameSettings` remembers the last landing.

```
Title ─ Play solo ─ Explore ──┐
Title ─ Multiplayer ─ Join ───┤── MapScreen (Landing role) ── Loading ── InWorld
Title ─ Map ──────────────────── MapScreen (Library role)
```

A command-line run with `--at`, and every probe, skips the map exactly as it skips the title today
(`GameShell.UseTitle`).

## Phases

| # | What | Why it is its own phase |
|---|---|---|
| **0** | Extract `tools/MapCore` from `tools/MapSetup`; the terminal tool becomes a front-end on it. No behaviour change. | A pure move, verifiable by the terminal tool's own output being unchanged. |
| **1** | Port the swisstopo STAC download to C# in MapCore: paging, HEAD-and-manifest skip, parallel jobs, byte-range fetch for big files, SHA-256 verify, `.part` resume. **Python eliminated.** | Must stay compatible with `swiss_data.py`'s manifest, or a machine that used either tool re-downloads everything. |
| **2** | Retarget `TerrainPreprocessor` to net8, give it a library entry point, drive the stages in-process from MapCore. **.NET SDK eliminated.** | Verified by building a small region both ways and diffing the tiles byte for byte. |
| **3** | The game references MapCore. `MapScreen` + `MapCanvas`: relief map, status overlay, search, selection, estimate table, Requirements panel. Keyboard, mouse, gamepad. "Map" on the main menu. | The whole UI, and the first point at which a player can see what they have. |
| **4** | `DownloadJob` in the background, and live tile arrival: manifest hot-reload, generated fill dropped and re-blended where real data landed. | The only phase that touches terrain streaming; the one with real risk. |
| **5** | Landing picker: the map on launch and join, `WorldLaunch` landing, last-place memory, the no-terrain-here notice. | Touches joining, so it is the phase that needs the network tier. |
| **6** | A C# FileGDB reader for buildings and cycle routes. **GDAL eliminated.** Done, #537. | Independent of everything above; until it lands, those two layers carry the setup notice. |

## Risks

- **Live tile arrival (phase 4)** is the hard part. Tiles becoming real under a flying player means
  re-blending the generated fill at a moving boundary. If it proves ugly, the fallback is to apply
  newly built tiles on the next world load and say so in the UI — the download still runs in the
  background, only its effect waits.
- **Download parity (phase 1)**. The C# port must agree with `swiss_data.py` on the manifest and on
  the checksum check, or both tools will fight over the same folder.
- **Preprocessor retarget (phase 2)**. No net9-only API was found, but `ServerGarbageCollection`
  and the heavy parallel stages now run inside the game process, which has its own GC settings
  tuned for tiles (`System.GC.ConserveMemory`). Needs a memory-pressure check on a large region.
- **Release size**. Nothing new ships: Python and the SDK are removed rather than bundled, and
  MapCore adds 425 KB of embedded country map.

## Testing

- `tools/test.sh quick` on every phase.
- A new `--mapcheck` probe, alongside `--menucheck`: the map opens, relief and status layers build,
  a search picks a town, a rectangle selects, the estimate table fills, a download starts and
  cancels, the screen closes clean.
- Phase 2: a small region built in-process and by the CLI, tiles diffed.
- Phase 4: a probe that starts a download, enters a world, and asserts a tile goes from generated
  to real without a crash or a seam.
- Phase 5 is network-touching, so **tier 2 (`tools/test.sh net`)**, checking the landing on the
  joining peer.
