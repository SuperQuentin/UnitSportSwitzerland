# Android client: play on a phone against a PC server

Status: **proposed** (issue #63), nothing built yet.

## Goal

An Android phone runs the game as a **client** and joins a dedicated server running on a PC. The
phone never runs the server. It ships without the 5.3 GB `terrain_chunks/` and streams the tiles
it needs from the server.

Out of scope: iOS, a phone-hosted server, the Play Store, and shipping real terrain in the APK
(world generation fills anything not streamed).

## Why it is feasible

- **Engine.** Godot exports C#/.NET projects to Android (arm64). The web target is the one C#
  cannot use; Android works.
- **Renderer.** `project.godot` already uses `renderer/rendering_method="mobile"` (Vulkan). Older
  GPUs can fall back to Compatibility (OpenGL ES 3).
- **Network.** ENet runs on Android the same way it runs on desktop.
- **Terrain without shipping it.** `src/Terrain/NetworkChunkSource.cs` already covers a client with
  no local tiles: local directory → `user://chunk_cache/` → server over ENet, with a size cap and
  oldest-first eviction (`EvictIfOversized`).
- **Joining from the UI.** `src/Core/MainMenu.cs` has a "Join a server" mode, so a client can
  connect without command-line flags.
- **Style.** Low-poly PS1-style meshes and textures are cheap on mobile GPUs.

## What blocks it today

| Area | Problem | Where |
|---|---|---|
| Data paths | `FindChunkDir()` looks next to the executable, then at `res://terrain_chunks`. On Android `res://` is inside the APK, where `System.IO` cannot read. | `src/Core/TerrainPaths.cs` |
| Data reads | Plain `System.IO` reads rooted at the chunk dir: place index, manifest, ambience. | `PlaceSearchUi.cs`, `ClientTerrainSync.cs`, `Audio/Ambience.cs`, `Terrain/LocalChunkSource.cs` |
| Command line | Around 20 call sites read `OS.GetCmdlineUserArgs()`, and a phone passes none. Most are debug or probe flags, but `--connect` and the settings overrides matter. | `ClientWorld.cs`, `NetworkManager.cs`, `GameSettings.cs`, `Main.cs`, … |
| Input | No touch handling. Input assumes a keyboard, a mouse (about 34 mouse-mode or mouse-motion sites) or a gamepad. | `src/Core/PlayerInput.cs`, `src/Player/*` |
| Desktop-only code | `VideoExporter` starts `ffmpeg` with `Process.Start`. `ServerConsole` reads stdin. | `src/Gpx/VideoExporter.cs`, `src/Net/ServerConsole.cs` |
| Performance | Tiles allocate 1–4 MB buffers on the large-object heap. About 54 thread and task sites build meshes in the background. LOD rings and the horizon are sized for a desktop GPU. | `src/Terrain/ChunkManager.cs`, `GameSettings` |

## Phases

### 0. Spike: does it run at all? (go / no-go)

1. Install the Android SDK, JDK 17 and the Godot 4.7 .NET export templates. Add an Android preset
   (arm64-v8a only) to `export_presets.cfg`.
2. Export a debug APK with **no** `terrain_chunks/`, then install it with `adb install`.
3. On the PC: `<godot> --headless --path . -- --server --generated-world`. On the phone: "Join a
   server" at the PC's LAN IP.
4. Measure frame rate, memory (`adb shell dumpsys meminfo`) and heat over about 10 minutes on
   foot, then in a car. `PerfOverlay` and `PerfRecorder` already exist.
5. Connect a Bluetooth gamepad to test movement. This only lets the spike measure performance
   before touch exists; touch is still required for the first version (phase 3).

Stop here if a mid-range phone can't reach about 30 fps with a reduced render distance.

### 1. Storage and paths

- `TerrainPaths.FindChunkDir()`: on `OS.GetName() == "Android"`, return
  `ProjectSettings.GlobalizePath("user://terrain_chunks")`, which is a real filesystem path, so
  `System.IO` keeps working. No `res://` fallback.
- Check every `System.IO` read that joins onto the chunk dir or `res://`. Each file either comes
  from the server stream or cache, or moves to Godot's `FileAccess`.
- Decide the stream-cache cap for phones: a lower default than desktop, set in settings.

### 2. Launch without a command line

- Save the last server address in `GameSettings` so "Join a server" fills it in.
- Leave debug and probe flags desktop-only. If a phone ever needs one, read an optional
  `user://args.txt` in one place, not at every call site.

### 3. Touch controls (required)

This is the main way to play on a phone, not an optional extra.


- A touch overlay (a `CanvasLayer`) that feeds the same actions `PlayerInput` already reads:
  - a left virtual stick for movement;
  - a right-side drag for the camera;
  - context buttons per mode (jump or interact on foot; brake or handbrake in a car; throttle and
    roll in flight).
- Show the overlay on touchscreen devices, and hide it while a gamepad is being used.
- Menus: check that hit targets are large enough and that `UiFocus` handles touch.

### 4. Mobile performance profile

- A "Mobile" preset in `GameSettings`: shorter render distance, fewer or smaller LOD rings, a
  cheaper horizon, no or low-resolution shadows, and a lower render scale.
- Check GC behaviour on the Android runtime (`ConserveMemory=7` in the csproj) under tile churn.
- Cap background mesh-build concurrency by core count, so big.LITTLE CPUs don't throttle.

### 5. Platform gating

- Hide or disable GPX video export (ffmpeg), the server console and server mode on Android.
- Home-trainer input: check which transport it uses, and whether it can work on Android or should
  be hidden.

### 6. Multiplayer verification

Follow the project rule: PC dedicated server plus a desktop client plus the phone client on the
same LAN. Check replication, authority, animation and damage **on the remote peer**, in both
directions (phone sees desktop, desktop sees phone).

## Decisions (agreed)

| Question | Decision |
|---|---|
| Distribution | **Sideloaded APK** for now. No Play Store, so no AAB, upload key or target-SDK policy yet. |
| Input | **Touch controls are required** for the first version. A gamepad is a fallback, not a replacement. |
| Real terrain in the APK | **None.** World generation covers anything the server does not stream. |
