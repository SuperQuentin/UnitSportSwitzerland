# Three clocks: environment time, simulation speed, real time

Status: **planned**, nothing built. Tracking issue: #579.

| Phase | State | What it does |
|---|---|---|
| 1 `RealClock` | not done | An unscaled wall clock and frame delta, so the real-time bucket survives a time scale |
| 2 Name the buckets | not done | `SimClock` over `GameClock`, `WorldClock.EnvNow`, and the rule note that says which clock a system belongs to |
| 3 Server-owned sim speed | not done | The server broadcasts `(scale, applyAt)`; every peer flips `Engine.TimeScale` at the same server instant |
| 4 Move the misplaced timers | not done | The ~10 simulation timers currently on the wall clock move to sim or env time |
| 5 Guards | not done | A lint check for wall-clock use in gameplay, and a two-peer probe that sim speed is in sync |

## Goal

Every timed system in the game reads one of exactly three clocks, and the two that describe the
world are owned by the server so that every peer agrees.

- **Environment time** — the world's own pace: time of day, traffic and railway signals, plant and
  build growth, campfire burn, craft stations, resource regrowth, fishing odds, the dawn chorus,
  clocks on walls. Server-owned, already most of the way there as `WorldClock` (#452).
- **Simulation speed** — everything that follows physics: vehicles, player movement, projectiles,
  weapon rate of fire, AI and NPCs, ragdolls, damage windows. Server-owned, new.
- **Real time** — UI, audio presentation, network plumbing, persistence stamps, force feedback,
  waiting on worker threads. Per-process, never synced, never scaled.

Out of scope: per-player time scales, rewind or replay, and making environment time follow
simulation speed (decided against below).

## Two decisions taken up front

**Environment time does not follow simulation speed.** It keeps its own pace off
`ClockSync.ServerNow`, as it does today. At 0.25× the cars crawl, but the sun and the traffic
lights carry on at their normal rate. The accepted consequence is that signal-following AI runs
slow against normally-cycling lights, so a crawling car can sit through a whole green; slow motion
is an offline debug tool and that is tolerable. The alternative — env time derived from a
sim-scaled server clock — would keep the world internally consistent but means rebuilding
`WorldClock`'s epoch maths on a clock that does not exist yet.

**Simulation speed is applied as `Engine.TimeScale` on every peer.** `GameClock.Now` is
`Engine.GetPhysicsFrames() / Engine.PhysicsTicksPerSecond`, so it already reads simulated seconds
under a time scale, and every `delta`-driven gameplay timer already follows. That makes the
gameplay churn for this phase approximately zero. The price is collateral damage on the real-time
bucket, which phase 1 pays off first.

## Where we start

Two of the three clocks exist:

- `src/World/WorldClock.cs` (#452) is the environment clock, and it is already right: the server
  owns `(hour0, epoch, minutesPerDay)`, those three numbers cross the wire on join and on each
  `/time`, every peer turns them into "the hour now" from its own estimate of the server clock, and
  nothing is summed frame by frame, so nothing drifts and a late joiner sees the same sky. `/time`
  is admin-gated in `ChatManager`. It persists across a dedicated server's restart.
- `src/Core/GameClock.cs` (#461) is the simulation clock. It respects both `Engine.TimeScale` and
  the quick tier's `--fixed-fps`.
- `ClockSync.LocalNow` / `ServerNow` / `ServerUnixNow` is the real clock, plus `Time.GetTicksMsec`
  directly in many places.

What is missing is that simulation speed is not server-owned at all — `DebugMenu.SetTimeScale`
sets `Engine.TimeScale` locally and refuses outright when online — and that roughly ten simulation
timers read the wall clock instead of either world clock.

## Phase 1 — `RealClock`, and fixing the real-time bucket

`Engine.TimeScale` scales `_Process` and `_PhysicsProcess` delta for the whole process, and Godot
offers no unscaled per-frame delta. So before a time scale can be switched on in anger, anything
that must stay real needs a source that a scale cannot touch.

- Add `src/Core/RealClock.cs`: `Now` (monotonic seconds, `Time.GetTicksUsec`) and `Delta`, the
  unscaled frame delta, measured once a frame from `Time.GetTicksUsec` deltas rather than taken
  from the engine.
- Fix `ClockSync._Process`: it accumulates its ping period from scaled `delta`, so at 0.1× pings
  would drop from every 2 s to every 20 s and the clock sync would degrade exactly when the rest of
  the design depends on it. It moves to `RealClock.Delta`.
- Audit the other `delta`-driven network and UI cadences for the same bug. The ones that read
  `Time.GetTicksMsec` directly (`Handshake`, `InterestService`, `ServerStats`, `Swarm`, the chat
  rate limit) are already safe and stay as they are.
- Decide per case whether HUD and menu animation should slow with the world. The world-space HUD
  probably should; menus should not.

No behaviour change at scale 1. Quick tier.

## Phase 2 — Name the buckets

Nothing functional, but it is what makes the rule enforceable later.

- `WorldClock.EnvNow`: environment seconds since the epoch, monotonic and unwrapped, alongside the
  existing `Hour`, derived the same epoch way. Growth and burn need a counter that does not wrap at
  24 h; `Hour` stays for the sky.
- Persist `EnvNow` in `user://world_clock.cfg` next to `hour` and `minutes_per_day`, so a
  restart does not reset everything that is mid-growth. The saved `hour` alone loses the day count.
- `SimClock` as the documented name for `GameClock.Now` in gameplay, so the three buckets read as
  three names at the call site.
- A `docs/notes/core/three-clocks.md` note with the bucket rule and the table of which system is in
  which, replacing the looser wording in `docs/notes/general/fast-checks.md`.

**The unit trap, worth stating loudly:** the default day is 24 real minutes, so environment time
runs 60× real time. A duration moved from the wall clock into env time must be re-expressed in env
units, never copied across. `CampfireClock.BurnSeconds` is `20 * 60` *real* seconds today; read as
env seconds at the default day length that is 20 real seconds. Each constant moved in phase 4 gets
re-tuned as a fraction of a day, not renamed.

## Phase 3 — Server-owned simulation speed

- The server owns `(scale, applyAtServerNow)` and broadcasts it, the same shape `WorldClock` uses.
  Applying on receipt instead would let peers flip at different instants and rubber-band the
  replicated bodies for the width of the RPC spread; scheduling the flip at a future `ServerNow`
  makes every peer change at the same server instant.
- Sent on join as well as on change, like `WorldTime` in `ChatManager.Handshake`.
- A `/speed` chat command, admin-gated, mirroring `/time speed`: `/speed 0.25`, `/speed 1`. Bounds
  it the way `TimeCommand` bounds day length.
- `DebugMenu`'s existing Time ×0.1–×4 picker routes through the same path instead of setting
  `Engine.TimeScale` directly, and stops being offline-only. Offline, "the server" is this process,
  so it applies immediately.
- Not persisted: a restarted server comes back at 1×.
- `--fixed-fps` must not combine with a scale ≠ 1; the quick tier runs at 1× and should assert it.

Replicated state, so **tier 2** (`tools/test.sh net`), checking the scale on the **remote** peer.

Deliberately **left on the wall clock**: the server-side shot guard at `Items/ItemEvents.cs:204` is
anti-cheat rate limiting, so real time is correct — a client that slowed its own simulation must not
be allowed to fire faster. Likewise `ClockSync`, `Handshake`, `InterestService`, `ServerStats`,

presentation (audio chimes, UI pulses, camera shake, cloth sway).

Borderline, to decide when touched: `Build/BuildTool.cs:270` (250 ms place repeat — input, not

(0.25 s fresh-open guard), `Player/FootPlayer.cs:1951` (0.5 s dance crowd poll),

`--fixed-fps`).

## Phase 5 — Guards

- A lint-style unit check: no file under the gameplay directories reads `Time.GetTicksMsec`,
  `Time.GetTicksUsec` or `Time.GetUnixTimeFromSystem` unless it is on an explicit allow-list with a
  reason. This is the only thing that stops the three buckets rotting back into one.
- A two-peer probe that the simulation scale matches on both peers after a `/speed`, and that a
  replicated body's position does not jump across the flip.
- A probe that `EnvNow` survives a server restart and that nothing mid-growth resets.

## Risks

- **`Engine.TimeScale` is a blunt instrument.** It scales audio pitch, particle systems and
  animation players too. Phase 1 can only fix what reads a delta; anything the engine scales
  internally will slow down whether we want it to or not. Phase 3 should be tried at 0.25× and
  4× with a careful look at audio and particles before it is called done.
- **Scale ≠ 1 online is new ground for replication.** `FootPlayer` net timestamps are real time
  while bodies move in simulated time. With a uniform scale on every peer this stays consistent,
  but the transition window is the risk, which is why the flip is scheduled rather than immediate.
- **Re-tuning env durations is a gameplay change, not a refactor.** Phase 4's env moves will make
  fires and regrowth feel different. Worth doing in a separate commit from the mechanical ones so
  it can be reverted on its own.
