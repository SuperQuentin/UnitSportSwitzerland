# Website accounts and the admin dashboard

Asked by the owner on 2026-10-25:
- **Accounts on the site**: create an account and sign in on the website (the same Nakama accounts as the game).
- **Admins see a Dashboard button.** The dashboard holds:
  - server editing: live settings, restart and update, startup settings, the players online;
  - a virtual live console;
  - user management: search and view, admins, ban and unban. Delete and rename are out for now.
- **The first admin** is `quentin.aellen@infrack.ch`.

## Who is an admin

- **The admins are a Nakama group, `admins`.**
- **The first admin is bootstrapped by email.** `NAKAMA_ADMIN_EMAILS` in the host's Nakama `.env` reaches the module as
  a runtime env var (`--runtime.env`). An account with one of those emails is added to the group the first time it calls
  `me`.
- **The module decides.** Every admin RPC (`tools/nakama/modules`) checks the caller's membership itself. The page only
  hides the button; it never grants anything.
- **The game server asks Nakama.** It calls `me` with the player's token (cached for a minute) for the dashboard's
  server API. In the game, an account in `admins` gets admin rights on servers that check accounts, besides `admins.json`.

## Phase 1: accounts on the site, the admin role, the Users tab

- **Nakama module RPCs**, each with a session (never the http key):
  - `me` returns `{id, username, email, admin}`, and runs the bootstrap;
  - `admin_users {q}` searches by name or email (SQL, 50 results);
  - `admin_user {id}` returns created, banned, admin and the course results;
  - `admin_set_admin {id, admin}`;
  - `admin_ban {id, ban}`: `nk.usersBanId` / `nk.usersUnbanId`. A ban also logs the account out. A banned account
    cannot sign in, so servers that check accounts refuse it.
- **The site** (`tools/deploy/web/`):
  - `account.js`: a shared sign-in and create-account panel for every page, through `/nakama/`. The server key comes
    from `nakama.json`, which the deploy writes. The session lives in `localStorage`, renewed by its refresh token.
  - The nav shows "Sign in", or the player's name with Sign out, and **Dashboard** for admins.
  - `admin.html` has three tabs: **Users** (phase 1), **Server** and **Console** (phase 2).
- **Caddy** serves `/admin.html`, `/account.js` and `/nakama.json`.

## Phase 2: the game server's admin API, the Server and Console tabs

**Status (2026-10-25, #1211):** built as below, with these changes. Live settings are the existing commands (`/time`,
`/weather`, `/seastate`, `/speed`, `/say`) run from the page, their replies shown; no new teleport rule or message of the
day yet. A player is kicked from the table; sending one to the spawn is left out (`/spawn` needs the admin's own body).
Startup arguments are a checked line, not a form.

- **`--admin-http 127.0.0.1:7790`**: a loopback HTTP listener in the dedicated server, modelled on
  `Playtest/LoopbackHttp` (raw `TcpListener`, Host and Origin checked, body capped).
  - Caddy proxies `/server-api/*` to it.
  - Every request carries `Authorization: Bearer <Nakama token>`, checked by `me` (admin) with a one-minute cache.
- **Endpoints**:
  - `GET /log?after=<seq>`: a ring buffer of the server's log lines (a Godot `Logger`, as `PlaytestLog`), polled every
    second by the Console tab.
  - `POST /command {line}`: `ChatManager.RunConsoleCommand` as a named pseudo-peer whose replies are captured and
    returned. Every command is logged with the admin's name.
  - `GET /players`: name, account, position, ride, ping (ENet RTT), admin.
  - `POST /players/{peer}/kick {reason}`, and `/spawn` to send the player to the spawn point.
  - `GET` and `POST /settings` for the live settings: time of day and day length (`WorldClock`), weather
    (`SnowService`), sea state, the teleport rule (`Arrival`: a setter plus a re-send), and a message of the day shown
    on join (new).
  - `POST /restart {minutes}`: warn the players, then quit. `start-server.sh run` loops on a `restart-requested` marker,
    as it does on `pending-update`.
  - `POST /update`: the existing `/update`.
  - `GET` and `POST /startup`: `$DEPLOY_DIR/server-args.local`, which `start-server.sh` appends to the deploy's
    arguments. It holds `--accounts`, `--server-name` and the other startup settings, applied on the next restart. The
    deploy never overwrites it.
