# Adventure: progress store, objectives and the quest log

Status: **planned**. Tracking issue: #1223 (overview: #1228).

One of the five Adventure plans (phases 1 and 2), written together: `adventure-places` (POIs,
discovery, fog, Swiss Atlas), `adventure-navigation` (compass, pins, quest marker, fast travel),
`adventure-stamina` (stamina, climbing, lift), `adventure-rewards` (chests, edelweiss, trials,
photo quests, gadgets). **This plan owns the two contracts the others build on**: the per-player
progress store (section 1) and the adventure events (section 2). They land first, in their own PR.

| Part | State | What it does |
|---|---|---|
| 1 Progress store | planned | `AdventureBook`: per-player, server-kept, keyed by `PlayerKey` fingerprint; typed sections each system declares for itself, versioned |
| 2 Adventure events | planned | `AdventureEvents`: the server-side bus other systems raise (POI found, chest opened, trial done...) |
| 3 Service and switch | planned | `World/Adventure` on server and clients, offline playing the server's part; `Systems.Adventure`; off in a BR round |
| 4 Quest framework | planned | `QuestDef` catalog in plain C#, step kinds, `QuestEngine` matching events, rewards, quest sources (dailies later) |
| 5 Quest log and tracker | planned | `Ui/AdventureLog` (tabs other plans add), `Ui/QuestTracker` HUD, toasts, the tracked target for navigation |
| 6 Starter quests | planned | Five quests that exercise the other four plans |
| 7 Checks and notes | planned | Tier-0 tests, an offline quick probe, `tools/adventurecheck.sh` (net), notes and map rows |

## Goal

A player's adventure progress (what they found, opened, unlocked, finished) is one store that every
Adventure system writes to through its own section, kept by the server under the player's proven
identity, so a name typed by someone else never reaches it. Quests are data: a new quest is a catalog
entry whose steps listen to events the other systems already raise, never new code in those systems.

Out of scope: NPC quest givers with dialogue, party/shared quests, carrying progress between servers
or from offline to online, the Postkarte daily generator itself (only its seam, 4.6), leaderboards.

## 1. The progress store (`src/Adventure/`, namespace `UnitSport.Adventure`)

Plain C#, no Godot, linked into `tests/UnitSportSwitzerland.Tests` like `SleeperBook` and `InviteBook`.

- **`SectionKey<T>`** (`where T : class, new()`): a system's handle on its slice of a player's progress.
  Declared **in the owning system's own file**, never in a central list:
  ```csharp
  public static readonly SectionKey<PlacesProgress> Section =
      new("places", Version: 2, Migrate: (JsonNode old, int from) => PlacesProgress.Upgrade(old, from));
  ```
  `Id` is a stable lower-case string (the JSON key), `Version` the shape's version, `Migrate` turns an
  older JSON into the current `T` (null = deserialize as is). `T` is a plain DTO serialized with
  `AdventureJson.Options` (one static `JsonSerializerOptions`, `json-store` rule).
- **`PlayerProgress`**: one player's sections.
  - `T Get<T>(SectionKey<T> key)`: decodes the section on first use (lazy, migrating if its saved
    version is older), or makes a `new T()`; the same instance after that.
  - `void Touch(SectionKey<T> key)` (or `Touch(string id)`): marks it dirty after a change; the service
    saves and syncs dirty sections (3.3). Mutating without `Touch` is a bug the tests catch.
  - Sections in the file that no running code asked for (a system off under `--systems`, a newer
    build's section) stay as raw `JsonNode` and are **written back unchanged**: nothing is lost by a
    build or a run that does not know them. A saved version **newer** than the code's is kept raw and
    `Get` returns a read-only empty `T` with a warning (a downgrade never overwrites newer data).
  - `string Key` (fingerprint), `string LastName` (shown in admin tools only), `long Created`, `long Seen`.
- **`AdventureBook`**: `PlayerProgress For(string key)`, `bool TryGet(key, out p)`, `Forget(key)`
  (unloads on leave after saving), `string ToJson(PlayerProgress)`, `PlayerProgress FromJson(string)`.
  Loads one player at a time: progress is per player file, not one big file (fog alone may be KBs).
- **File shape** (`AdventureFile`, version 1):
  ```json
  { "v": 1, "key": "9f2c...", "name": "Lea", "created": 1793000000, "seen": 1793004000,
    "sections": { "quests": { "v": 1, "data": { ... } }, "places": { "v": 2, "data": { ... } } } }
  ```
  The file's `v` covers the envelope only; each section migrates itself.
- **Sections the other plans add** (each in its own file, ids reserved here):
  `places` (discovered POIs, viewpoints synced, canton counts), `fog` (map fog bitmask, its own delta
  RPC), `travel` (unlocked travel points), `stamina` (max stamina bonus, upgrades bought), `collect`
  (edelweiss and collectibles taken), `chests` (opened chest ids), `trials` (best times, medals),
  `photos` (photo targets taken), `quests` (this plan, 4.4), `gadgets` (owned adventure gadgets),
  `pins` (map pins, `adventure-navigation`).

## 2. Adventure events

`src/Adventure/AdventureEvents.cs`, plain C#. Raised **on the server only** (offline: on the client
playing the server's part, 3.2), always after the raising system has checked the act and written its own
section. Objectives listen; nothing listens on clients (they get progress through 3.3).

```csharp
public abstract record AdventureEvent(long Peer, string Key);            // Key = PlayerKey fingerprint
public sealed record PoiDiscovered(long Peer, string Key, string PoiId, string Kind, string Canton) : AdventureEvent(Peer, Key);
public sealed record ViewpointSynced(long Peer, string Key, string PoiId, string Canton) : AdventureEvent(Peer, Key);
public sealed record CollectibleTaken(long Peer, string Key, string CollectibleId, string Kind, string Canton) : AdventureEvent(Peer, Key);
public sealed record ChestOpened(long Peer, string Key, string ChestId, int Tier, string? PoiId) : AdventureEvent(Peer, Key);
public sealed record TrialFinished(long Peer, string Key, string TrialId, double Seconds, int Medal) : AdventureEvent(Peer, Key);
public sealed record PhotoTaken(long Peer, string Key, string TargetId, string? PoiId) : AdventureEvent(Peer, Key);
public sealed record TravelUnlocked(long Peer, string Key, string PointId, string Kind) : AdventureEvent(Peer, Key);
public sealed record ItemObtained(long Peer, string Key, ItemId Item, int Count, string Source) : AdventureEvent(Peer, Key);
public sealed record ItemDelivered(long Peer, string Key, ItemId Item, int Count, string TargetId) : AdventureEvent(Peer, Key);
public sealed record Interacted(long Peer, string Key, string TargetId) : AdventureEvent(Peer, Key);
public sealed record QuestCompleted(long Peer, string Key, string QuestId) : AdventureEvent(Peer, Key);
```

- **`AdventureEvents`** (the bus, a field of the service): `void Raise(AdventureEvent e)` and
  `event Action<AdventureEvent>? Raised`. Synchronous, main thread, no allocation beyond the record.
  `Raise` drops an event whose peer is not adventuring now (`AdventureService.Active(peer)` false, e.g.
  a BR participant; an unproven peer still counts, on session progress, 3.1). No per-event log line.
- New events are new records **in the raising system's file** deriving from `AdventureEvent`; the
  quest engine matches by type, so adding one edits nothing here. The list above is the shared set.
  Added by the other plans in their own files: `CantonMilestone` and `ChapterCompleted` (places),
  `StaminaRaised` (stamina), `EdelweissOffered` (rewards).
- Ids are strings owned by their plan: `PoiId` (places: stable across preprocessor runs, see open
  questions), `ChestId`/`CollectibleId`/`TrialId` (rewards), `PointId` (navigation), `TargetId` for
  photos, deliveries and interactions = a `PoiId` or an `area:<name>` from the catalog (4.2).
- `Kind` and `Canton` are strings (`"pass"`, `"UR"`) so this file depends on no other plan's enum;
  cantons are the two-letter codes.

## 3. The service and the switch

### 3.1 `AdventureService` at `World/Adventure`

`src/Adventure/AdventureService.cs`, a `Node`, server and every client (RPCs route by path, as
`World/Bank`, `World/Sleepers`). `AdventureService.Instance` (null when the system is off: every user
calls `?.`). Created in `ServerWorld._Ready` beside the sleepers and in `ClientWorld` beside
`Items.Bank.Create`, both under `if (Systems.On(Systems.Adventure))`.

- **Identity**: `Net/Sleepers` already proves each peer's `PlayerKey` (`Challenge`/`Prove`). It gains
  `public string? KeyOf(long peer)` and `public event Action<long, string>? Proven` (raised after
  `_keyOf[peer] = key`). The service loads `user://adventure/players/<key>.json` on `Proven`, then sends
  the owner every section (`SectionSync`). Never keyed by name: `ChatManager.NameOfPeer` is only stored
  as `LastName`.
- A peer that never proves (old client, bot, key already connected) gets **session progress** under
  `peer:<id>`: works, never saved; its client is told once (`Unsaved` RPC, a line in the log's header).
- `PeerLeft(peer)`: saves dirty sections, then `Forget`. Called from `ServerWorld.OnPeerDisconnected`
  next to `_sleepers.PeerLeft` (both before the registry forgets the peer).
- `public bool Active(long peer)`: system on, peer known, and not in a Battle Royale round
  (`BrManager.Playing(peer)` or in its lobby, the delegate `InMatch` set by `ServerWorld` as for
  `Structures.InMatch`). Inactive peers keep their progress; events are dropped, the tracker hides.
- Server API for every other plan (and for bots, rule 2):
  `PlayerProgress? Progress(long peer)`, `void Touch<T>(long peer, SectionKey<T> key)`,
  `AdventureEvents Events`, `void Grant(long peer, Reward r, string why)` (4.5),
  `void RegisterReward(string kind, Func<long, PlayerProgress, string, string?> apply)` (4.5).

### 3.2 Offline: the client plays the server's part

Offline Explore has **no in-process server** (`Launch.Networked` false; `Bank`, `LootService`,
`PlacedObjects` all say "offline this client does both"). The service does the same, so there is one
code path: `_authority = server || !Launch.Networked`. With authority it owns an `AdventureBook`, the
local player is peer `1` with key `local`, and every "server" method is the same method; replies that go
`RpcId(peer, ...)` online are direct calls (`ToOwner(peer, ...)` helper). The file is
`WorldChoice.SavePath("user://adventure/local.json")`, so a test world keeps its own (core/test-worlds).
Hosting from the menu runs a real headless server (net/hosting): the host joins it as a client and is
keyed like anyone. Offline and online progress are separate, like the bank's two accounts.

### 3.3 Sync to the owner ("progress changed")

- Dirty sections are flushed once per server frame at most, and per player at most 4 times a second:
  `SectionSync(string id, int version, string json)` → the owner only (`RpcId`, reliable). The client
  keeps a mirror `PlayerProgress Mine` decoded by the same `SectionKey<T>`s and raises
  `event Action<string>? SectionChanged` (the section id). UIs refresh on it, never per frame.
- A section that changes in tiny steps over a large body (fog) may send its own delta RPC instead and
  call `Touch` only for the save; that plan says so.
- `QuestNote(string questId, int what, int step, int count)` → the owner, for toasts (4.7).
- Other players never receive anyone's progress (a name tag title is a later, explicit field).

### 3.4 `Systems.Adventure`

`Core/Systems`: `Adventure = "adventure"` added to the constants and `All`. Default (players): on in
Explore and Multiplayer. Off on test worlds unless asked: `Systems.On` treats it like `Generated`
(off while `WorldChoice.Active != null`), and `Parse` removes it from `--world fixture`'s default set; a
probe that wants it names it (`--systems ui,adventure`, or `--world fixture --systems ...,adventure`).
Off per peer during a BR round (3.1). The client also hides the tracker while `Permissions.InMatch`.

## 4. The quest framework

### 4.1 Definitions: a C# catalog, as recipes are

`src/Adventure/Quests/QuestCatalog.cs`, plain C#, the `Crafting/Recipes.All` idiom (records, small
builder helpers, one static array, checked by a tier-0 test). Not JSON files: the ids it references
(`ItemId`, POI ids) are checked at compile or test time, and quests ship with the build.

```csharp
public sealed record QuestDef(string Id, string Title, string Blurb, Step[] Steps, Reward[] Rewards)
{
    public string[] Requires { get; init; } = [];        // quest ids done first
    public string? Canton { get; init; }                 // for the log's grouping and the Atlas
    public Start Start { get; init; } = Start.FromLog;   // FromLog | OnEvent (auto, e.g. first POI) | Given (by a source)
    public bool Repeatable { get; init; }
    public string Source { get; init; } = "catalog";     // "catalog" | "postkarte" | ...
}
```

### 4.2 Step kinds

Steps run **in order**; each has a `Count` (default 1) and a short `Text` for the tracker.
`TargetRef` is `Poi(id)` or `Area(name, E, N, radiusM)` (LV95, `positions-on-the-wire`).

| Step | Advances on | Data |
|---|---|---|
| `Reach(TargetRef)` | the server sees the peer within the radius (2 Hz check of active `Reach` steps only, from `FootPlayer.NetGlobal`), or `PoiDiscovered` of that POI | target |
| `Discover(Count, Kind?, Canton?)` | `PoiDiscovered` matching; distinct POIs (ids kept in the step state) | filters |
| `Collect(Kind or ItemId, Count, Canton?)` | `CollectibleTaken` / `ItemObtained` matching | filters |
| `Deliver(ItemId, Count, TargetRef)` | `ItemDelivered` at that target (4.3) | item, target |
| `OpenChest(Tier?, PoiId?)` | `ChestOpened` matching | filters |
| `Trial(TrialId, MaxSeconds?, Medal?)` | `TrialFinished` matching | trial |
| `Photo(TargetId)` | `PhotoTaken` of that target | target |
| `Interact(TargetId)` | `Interacted` with it | target |
| `Unlock(PointKind?, PointId?)` | `TravelUnlocked` matching | filters |
| `Finish(QuestId)` | `QuestCompleted` | quest (chains) |

A step kind is a `Step` record with `bool Matches(AdventureEvent e, StepState s)`; a new kind from
another plan is a new record in its file. Every step may say `Reveal` (pin shown before it starts).

### 4.3 Deliveries and interactions

- **Deliver**: the inventory is the client's (`items/inventory`, `cash-account`), so the server can
  check *where*, not *what*. At the target the log or the prompt offers "Hand over" (`interact` on the
  target's marker, 5.4): the client sends `RequestDeliver(questId, step)`; the server checks the quest,
  the step and the distance from the peer's `NetGlobal` to the target, answers `DeliverOk(questId, step)`,
  and only then does the client take the items (`Inventory.Take`), as cash leaves the pocket only when
  the bank answers. Server path `AdventureService.Deliver(peer, questId, step)`, then
  `Raise(ItemDelivered)`.
- **Interact**: raised by the interactable's own server method (a stall, a sign, a summit cross that
  the places plan places), never by the quest. Phase 1 interactables are POI markers (places plan).

### 4.4 Quest state: the `quests` section

```csharp
public sealed class QuestsProgress
{
    public Dictionary<string, QuestState> Active { get; set; } = new();   // quest id -> state
    public Dictionary<string, long> Done { get; set; } = new();           // quest id -> Unix time
    public string? Tracked { get; set; }
    public List<string> Titles { get; set; } = new();
    public string? Title { get; set; }                                    // the one worn
}
public sealed class QuestState { public int Step { get; set; } public int Count { get; set; }
    public long Started { get; set; } public List<string> Seen { get; set; } = new(); public int Seed { get; set; } }
```

`QuestEngine` (plain C#): `Start(progress, def)`, `Abandon`, `OnEvent(progress, e) -> QuestChange[]`
(step advanced, quest done), `Available(progress, sources)`. Pure: given a section and an event, the
changed state and what to tell; the service applies rewards and touches the section. At most 8 active
quests (25 with dailies), one tracked.

### 4.5 Rewards

`Reward` records: `Cash(int Chf)`, `Item(ItemId, int Count)`, `Title(string)`, `Unlock(string Kind, string Arg)`.
- `Cash` goes to the **account**, not the pocket (it should not be lost to a knock-out): a new
  `Bank.Credit(long peer, int amount, string why)` server method beside `Bank.Charge`, then
  `Bank.Report`/`SendBalance`; offline the local account, as `ClaimAll` does.
- `Item` goes to the owner like `LootService.Granted`: RPC `Granted(int item, int count, string why)`,
  the client adds it and drops what does not fit (`ChatManager.GiveOrDrop`).
- `Unlock(kind, arg)` calls the handler registered by the owning plan: `RegisterReward("stamina", ...)`
  (rewards/stamina), `"travel"` (navigation), `"reveal"` (places: lift fog round a POI). Unknown kind =
  a tier-0 catalog test failure.
- Rewards are applied once, server-side, in the same frame the quest moves to `Done` (one save).

### 4.6 Quest sources: dailies are a generator

`IQuestSource { string Id; IEnumerable<QuestDef> For(QuestContext ctx); QuestDef? Resolve(string questId) }`.
`QuestCatalog` is the first source. Phase 3's Postkarte errands are a second, `PostkarteSource`, whose
quests are generated from `(date, key, nearby POIs)` with ids like `postkarte:2026-10-27:3`: nothing but
the id and `QuestState.Seed` is saved, `Resolve` rebuilds the definition. `QuestContext` gives the
player's LV95 position, canton, `Done`, and the places catalogue. Not designed further here.

## Bots

Server-run bots have no `PlayerKey`, so they get session progress (`peer:<id>`). Every act is a server
method a bot could call: `Start(peer, questId)`, `Abandon`, `Track`, `Deliver(peer, questId, step)`, and
the raising systems' own methods. No brain uses quests in phase 1 (Adventure is off in BR, the only
bot mode). Rows in `bots/bot-capability-map`: "start / abandon a quest" (n/a phase 1; server path
`AdventureService.Start`), "deliver an item" (gap: a co-op brain, `MoveTo` + `Deliver`), "adventure
progress" (n/a: no identity, never saved).

## Network

- Authority: the server (offline the client in its place). Clients send requests only.
- Client → server: `RequestStart(string questId)`, `RequestAbandon(string questId)`,
  `RequestTrack(string questId)`, `RequestDeliver(string questId, int step)`. Each calls the server
  method of the same name with `GetRemoteSenderId()`; checks live in the method.
- Server → owner: `SectionSync(string id, int version, string json)`, `QuestNote(...)`,
  `Granted(int item, int count, string why)`, `DeliverOk(string questId, int step)`, `Unsaved()`.
- `Sleepers` gains `KeyOf`/`Proven` (no wire change). `Bank.Credit` reuses `Report`.
- Nothing replicates to other peers. **Protocol bump** (`Handshake.Protocol`, 49 today) in the PR that
  adds the node; later plans' own RPCs bump again.

## Persistence

- Server: `user://adventure/players/<fingerprint>.json`, one file per identity, through
  `JsonStore.SaveAsync` with `AdventureJson.Options` (`perf-saves-background`). Saved when a section
  is touched, debounced to once per 5 s per player, and at once on `PeerLeft`; `SaveQueue.Flush` on quit
  is already done by `Main`. A test world's server uses `WorldChoice.SavePath`.
- Offline: `WorldChoice.SavePath("user://adventure/local.json")`, same envelope, key `local`.
- Loaded on `Proven` (file read off the main thread is not needed: one small file per join).
- Migration: per section (`SectionKey.Migrate`); the envelope's `v` for the file layout.
