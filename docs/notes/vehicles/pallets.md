# Pallets a forklift lifts (#583, phase 2)

Plan: `docs/plans/forklift-and-pallets.md`. The machine is `forklift`; this is what it lifts.

- **In the model viewer** (`--models`, #622): rides show the forklift by themselves; `PalletNode` has a `[Showcase("Pallets")]` set (each goods on each deck, and a forklift carrying one), and the furniture set keeps `Pallet` though it is no longer in the merged mesh.
- **Which pallets**: a hall's **loose floor pallets** (`FurnitureType.Pallet`, `Lift == 0`:
  `InteriorMeshBuilder.IsLoosePallet`), 5-20 per warehouse or works. Pallets on racking stay drawn
  inside the `PalletRack` piece and are not liftable. And a site's **apron stacks** (phase 3,
  below).
- **Carved out of the merged mesh**, as a gun locker's door is (`AddLockDoors`):
  `InteriorMeshBuilder.Build` skips them and `InteriorManager.AddPallets` gives each a node of its
  own, `Items/PalletNode` (mesh from `PalletPiece(load)`, one box body). **No plan change, no
  `CurrentVersion` bump.** `--palletcheck` asserts a floor pallet adds exactly one `PalletPiece` to
  the merged mesh when lifted off the floor, i.e. is not in it.
- **The load byte** (`Items/Pallets`, tier 0, `PalletTests`) is a moved pallet's whole identity:
  seven bits of the goods roll the hall drew it with, one for the square 1.2 m aisle deck (the
  others are 1.2 x 1.0). A pallet of drums stays a pallet of drums, the same size. Hall pallets are
  drawn from the byte too (`PalletLoad(f)`), so one does not change when lifted.
- **Ids**: `"<building>:f<furniture>"` (a hall's), `"<building>:y<slot>"` (a yard's, phase 3),
  `"#<n>"` (one set down, numbered by the server for the session). `Pallets.TryParse`.
- **The fork rule** (`Pallets.Forked`), against `ForkliftLayout` (now a file of its own, so the unit
  tests link it): the pallet's centre inside the tines' rectangle in the machine's authored frame,
  the carriage under `ForkEntry`, the tines square to one of its sides, under 2 m/s. **Four-way**,
  as a Swiss or EUR pallet is: along its runners (its X) within 30°, or across them within 30°
  (`Pallets.Across`); at 45° the tines meet a corner block and nothing happens. Along-only was
  tried first and left every wall pallet unliftable: the wall placer stands them with their runners
  along the wall, their centre 0.5 m from it, so a 1.15 m machine cannot line up with the runners
  (the generated world's only warehouse near the spawn had exactly that). **Raised through `Pallets.Seat`
  (0.15 m) it is lifted; lowered under `SetDown` (0.12 m) it is set down**, where it rode
  (`ForkliftLayout.LoadCentre`, 0.12 m clear of the hull, on the ground the machine stands on).
  Seat over SetDown is the hysteresis: a pallet just set down is not picked straight back up.
  **No button**, so no new action on any device: the paddles already are (`forklift`).
- **On the forks** a pallet is part of the forklift: `Forklift.Carrying` (0, else 1 + load, plus
  `Pallets.AcrossBit` when forked across; ten bits in the parked flags above the ten of the fork
  height) rides `WritePose().Z` and `VehicleState.Flags`; `ForkliftMast.Carrying` draws
  `PalletNode.Carried(load, across)` on the carriage, `Seat` under the tines' top face, turned the
  way it was picked up (snapped square: up to 30° of turn when lifted), and it is set down so
  (`PalletNode.CarriedYaw`). So it crosses a bay's portal with the
  machine, a copy draws it from the pose, a parked machine keeps it, and nothing is on the wire
  per frame. No collider while carried.

## The server: `Items/PalletService` at `World/Pallets`

- Server-owned, **session-only** (the dormant vehicles' answer, #499): `Taken` (plan pallets that
  left their place) and `Loose` (set down, LV95 + altitude, so one in a hall 3 km down is as
  addressable as one in the yard). No disk format. `PlacedObjects` is deliberately not reused (the
  plan's four reasons: it persists, it has no carried state, it caps per owner, it has no
  deterministic original).
- `Tend(player, fork)` runs from `FootPlayer.WorkMast` for the local driver only: it asks
  `RequestTake(id)` / `RequestDrop(load, at, yaw)`, one request in flight, 0.5 s quiet after any
  answer so a refusal does not repeat every frame. It walks `PalletNode.All` (every pallet in the
  tree, hall and loose: a hall has 6-20) only while the forks are between `Seat` and `ForkEntry`.
- **Checked**: a hall pallet against its plan (`GetOrCreate`, `IsLoosePallet`; the load byte comes
  from the plan, never the asker), the asker on a forklift whose **published** forks
  (`Anim.Z` = `Carrying`) are empty to take, holding that load to drop, and within 4 m (LV95).
  Offline the client serves itself through the same methods, with no checks.
- `Took` / `Dropped` to everyone, `TakeRefused` / `DropRefused` to the asker, `Snapshot` on join
  (`ServerWorld.OnPeerAccepted`). Protocol 19.
- `Layouts`: where a plan comes from, `InteriorManager` unless set (the flat-world check sets it).

## Loot

`FurnitureType.Pallet` is a loot container (0.25). **A pallet still where the plan put it keeps
its loot exactly as before; one that has been moved is no container any more**:
`LootService.NearestContainer` skips it (`LootService.Moved`), and the server answers a search of
it with nothing and refuses a take. Its records key on the furniture index at a fixed spot, so a
shuffled pallet has nowhere to keep them. Put back on the same spot it is a loose pallet, still not
a container. A small, real loss, stated so it is not found later.
