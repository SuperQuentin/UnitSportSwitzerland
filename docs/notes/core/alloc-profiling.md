# Who allocates: GC pauses at speed (#1773)

A fast flight or drive is often **GC-bound, not commit-bound**: the workers that stream the world allocate hundreds
of MB a second, and every collection stops the main thread too. A sprint flight over Geneva (60 m/s, earth frame)
allocated ~400 MB/s, ran ~800 gen0 / 200 gen1 / 15 gen2 collections in 40 s and **paused 7 to 9 s of the 40**; the
flat world at the same speed allocated more (780 MB/s). The session perf log's hitches say `[other]` for these: it
only tells commits, GC counts and GPU apart.

## Measure

- `--creativefly 300,40,1,80 --at 2500956,1117569 [--frame earth|flat]` (`player/creative-mode`): frame
  percentiles, `gc gen0/gen1/gen2 paused N ms`, `allocated MB/s`, peak working set, the worst frames with the GC
  counts and pause inside each. `--allocs` adds MB/s by type (an in-process `EventListener` on the runtime's
  `GCAllocationTick`, one tick per ~100 KB a thread allocates).
- **Stacks**: `dotnet-trace` (global tool) on the running game, while it flies, for less time than is left (a trace
  cut by the process exiting has no rundown and does not parse):
  ```
  dotnet-trace ps            # the godot process with --creativefly in its command line
  dotnet-trace collect -p <pid> --providers "Microsoft-Windows-DotNETRuntime:0x1:5" --duration 00:00:00:20 -o t.nettrace
  ```
  then sum `GCAllocationTickTraceData.AllocationAmount64` by its `CallStack()` frames. TraceEvent ships inside the
  tool (`~/.dotnet/tools/.store/dotnet-trace/<v>/dotnet-trace/<v>/tools/net8.0/any/Microsoft.Diagnostics.Tracing.TraceEvent.dll`,
  nuget.org did not resolve here): a scratch console project referencing it by `HintPath`, built **outside the
  worktree** (`general/no-builds-inside-the-project`), ~30 lines:
  `new TraceLog(TraceLog.CreateFromEventPipeDataFile(path))`, then for each `GCAllocationTickTraceData` walk
  `ev.CallStack()` → `.Caller`, keep the `UnitSport.*` frames, sum inclusive per method and per (type, top frames).

- **CPU, the main thread** (#1910): `dotnet-trace collect -p <pid> --profile dotnet-sampled-thread-time --duration
  00:00:00:25` (this version's names: `list-profiles`; `cpu-sampling` is Linux-only). The pid must be the **game's**
  `Godot_v4.7.2-stable_mono_win64.exe`, never the `_console.exe` launcher in front of it (no .NET: the attach hangs). Sum the
  `Thread/Sample` events' stacks per thread: the main thread is the one whose stacks hold `_Process` most; group each
  sample by the first `UnitSport.*` frame under the engine's call (the node that paid). Each interop call shows (1-4 %
  for `IsInsideTree`, `GetTree`, `get_GlobalPosition`): per-frame code should ask the engine as little as it can. The
  analyzer (~80 lines, TraceEvent by `HintPath`) was at `E:\UnitSportSwitzerland\scratch\trace1910\analyzer`.

## The GC's own knobs

- `GCgen0size` (a 256 MB gen0 budget) cut gen0 collections 784 → 75 and the pause 7.2 → 2.6 s, but it is read from
  the environment only: `System.GC.Gen0Size` or `GCgen0size` in the csproj's `RuntimeHostConfigurationOption`
  reached `runtimeconfig.json` and changed nothing.
- **Server GC** (`System.GC.Server`, `HeapCount` 4, `NoAffinitize`: runtimeconfig knobs, honoured) cut the pause
  7.1 → 0.7 s and halved p95/p99. It changes every process's memory (the game, the server, every check the test
  runner admits by its peak RAM): a decision of its own, with numbers, not a side effect of a perf fix.
- `System.GC.ConserveMemory = 7` is already set (LOH compaction, `UnitSportSwitzerland.csproj`).
