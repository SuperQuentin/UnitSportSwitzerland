# Game windows on Windows: open, but never in front

- **The rule**: on the user's Windows machine an agent may open game windows (clients, probes,
  `--shot-queue`), but none may take the foreground or stay above the user's work.
- **A plain launch from the shell is fine**: `<godot> --path . -- ...` from an agent's shell opens
  its window behind the active one (checked 2026-10-02: VS Code kept the foreground the whole
  time). Godot calls `SetForegroundWindow` when it shows the window, but Windows refuses that call
  because the agent's process has no foreground rights. The live `ForegroundLockTimeout` on this
  machine is at its maximum. The registry says 0, but the registry is not the live value.
- **Never `--always-on-top`**: the window then sits above everything until it quits. Only
  `tools/style-shots.sh` uses it, and only on macOS (`macos-launch-steals-focus`): there, Godot
  stops drawing a covered window. On Windows a covered window keeps drawing.
- **Never `display/window/size/no_focus`** (project setting or `override.cfg`) as a way out: on
  Windows Godot gives a no-focus window `WS_EX_TOPMOST` too
  (`display_server_windows.cpp`, `_get_window_style`), so it stays on top.
- **Editor play takes focus**: stopping a game embedded in the editor's Game tab calls
  `SetForegroundWindow` on the editor (`remove_embedded_process`). That is the user's own editor,
  which has foreground rights. So `project_run` / stop through the godot-ai MCP brings the editor
  to the front. This comes from reading the source and is not measured. Run checks from the shell
  instead, and use editor play only when the user asks for it.
- **Mouse**: probes and tool runs set `MouseCapture.Disabled`, and `--nocapture` does the same for
  any other launch, so a background window never grabs the pointer.
