# iOS build: Xcode project on a macOS runner (#1025)

## How

- `tools/ios-build.sh` (a Mac with Xcode 26 and .NET 9): adds the `iOS` preset from `tools/ci/export_presets.cfg` to the local `export_presets.cfg` when missing, exports the Xcode project (`application/export_project_only`), then `xcodebuild` builds it **unsigned** for `generic/platform=iOS`. Output and logs: `test_output/ios/` (`export.log`, `msbuild.log`, `xcodebuild.log`, the `.app` under `dd/`). `--export-only` stops after the Xcode project.
- `.github/workflows/ios.yml` runs it on `macos-15` with Xcode 26 selected: by hand (`gh workflow run ios.yml`, once on `main`) or on a PR touching the iOS build files. Free (public repo). Not part of a release. The logs are the `ios-logs` artifact. Any push to such a PR cancels the running build and restarts it.
- **Takes ~2.5 h.** Godot runs `dotnet publish` with NativeAOT three times (`ios-arm64`, `iossimulator-arm64`, `iossimulator-x64`), ~45 min each on the 3-core runner, at one or two cores most of the time. The job allows 5 h. The export prints nothing meanwhile: the workflow's watchdog lists the running `ilc`/`clang` every 5 min.

## Walls hit, in order

- **Only on macOS.** Elsewhere Godot refuses: `Exporting to an Apple Embedded platform when using C#/.NET is experimental and requires macOS.`
- **Xcode 16 cannot link Godot 4.7's template**: it uses iOS 26 SDK symbols (`CADynamicRange*`, `MTLTensorDomain`). The runner's default is Xcode 16.4; the workflow `xcode-select`s the newest `Xcode_26*`.
- **The game is too big for one ARM64 dylib.** ~335 k lines of C#, ~15 MB of IL. Speed-optimised, NativeAOT's code spans ~134 MB, past the ±128 MB reach of an ARM64 branch:
  - `-ld_classic` (what .NET's ILCompiler uses by default) inserts no branch islands: `ld: b(l) ARM64 branch out of range`.
  - Xcode's current linker (`UseLdClassicXCodeLinker=false`) asserts on NativeAOT objects, on .NET 8 and .NET 9 alike: `ld: Assertion failed: … "too many large addends"`.
  - What works: `-ld_classic` with `OptimizationPreference=Size` and `IlcFoldIdenticalMethodBodies=true` (`UnitSportSwitzerland.csproj`, iOS only). **It will break again as the game grows.** The next steps then: leave dev-only code (trailer, model viewer, checks) out of the iOS build, or wait for an Apple linker that takes the object.
- **A failed `dotnet publish` still "succeeds".** Godot writes the Xcode project anyway, and `xcodebuild` builds an app with no game in it. Godot keeps the publish log in `~/Library/Application Support/Godot/mono/build_logs/<hash>_ExportRelease/msbuild_log.txt`; the script copies it to `msbuild.log` and stops on any MSBuild error.
- **SDL3's iOS library** (`ppy.SDL3-CS`) lands in the device folder as its simulator build (`linking in dylib … built for 'iOS-simulator'`). SDL only drives the steering wheel, which never starts on a phone (`core/platform`), so iOS excludes the package's native assets.
- `error: The specified item could not be found in the keychain.` during the export is harmless: no signing identity, and none is needed for the project alone.

## In the game

- iOS reads tiles from `user://terrain_chunks` like Android (`TerrainPaths`): `res://` is inside the pck.
- `Platform.IsMobile` already covers iOS: phone UI, no SDL, updater, hosting or VR.
