# GDAL setup (only `tools/swiss_relief.py` now)

> Since #537 **nothing in the terrain pipeline needs GDAL**: swissBUILDINGS3D and the ASTRA route
> networks are read from their FileGDB zips directly (`tools/TerrainPreprocessor/FileGdb.cs`). The
> only script left that imports `osgeo` is `tools/swiss_relief.py`, which rebuilds the embedded
> coarse heightmap and is run about once a release. The rest of this note is kept for that case.

- **What needs it**: only the Python exporters — `export_buildings.py` (swissBUILDINGS3D ->
  `buildings.gpkg`), the cycle-route step and `swiss_relief.py`. Terrain, roads, GWR and places
  are pure C# and work without it. The region setup wizard greys out "Buildings" and
  "Cycle routes" with `needs GDAL` until it is installed.
- **How the wizard checks**: it runs the first of `python`, `python3`, `py` that answers
  `--version`, then `<that> -c "import osgeo"` (`tools/MapSetup/Program.cs`, `FindPython`). It
  starts them **without a shell**, so a shell alias (`alias python=python3`) does not count; what
  matters is the executable on `PATH` (a pyenv shim, a venv, the system one). Install the bindings
  into *that* interpreter: `python -c "import sys; print(sys.executable)"`.
- **Check**: `python -c "from osgeo import gdal; print(gdal.__version__)"` prints a version.
  Restart the wizard afterwards; it checks once at start.

## macOS (Homebrew)

```sh
brew install gdal
python -m pip install "gdal==$(gdal-config --version)"
```

The pip step builds the bindings against Homebrew's libgdal, so the two versions must match
(`gdal-config --version`). Homebrew's own bindings only land in Homebrew's Python, not in a pyenv
or venv Python. After `brew upgrade gdal`, re-run the pip line, or `import osgeo` fails on the
changed library.

**`fatal error: 'utility' file not found`** during the pip build: a leftover
`/Library/Developer/CommandLineTools/usr/include/c++/v1` from an older Command Line Tools install
(a handful of files, no `<utility>`) shadows the SDK's libc++ headers, so no C++ compiles at all.
Point the build at the SDK's headers:

```sh
CPLUS_INCLUDE_PATH="$(xcrun --show-sdk-path)/usr/include/c++/v1" python -m pip install "gdal==$(gdal-config --version)"
```

or remove the stray folder for good (`sudo rm -r /Library/Developer/CommandLineTools/usr/include/c++`).

## Linux / WSL (Debian, Ubuntu)

```sh
sudo apt install gdal-bin libgdal-dev python3-gdal
```

`python3-gdal` covers the system `python3`. For another interpreter (pyenv, venv), use
`python -m pip install "gdal==$(gdal-config --version)"` as on macOS.

## Windows

PyPI has no Windows GDAL wheel (`pip install gdal` tries to build from source and fails). Install
the wheel matching your Python from https://github.com/cgohlke/geospatial-wheels/releases
(`gdal-<ver>-cp313-cp313-win_amd64.whl` for Python 3.13), e.g. `python -m pip install <url>`. It
includes the OpenFileGDB and GPKG drivers.
