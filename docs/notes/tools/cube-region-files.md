# Region-wide files in Earth positions, MapSetup's cube steps (G2 B3 row 8, #1507)

The last row of the B3 table (`docs/plans/global-tiling-g2.md`). Code: `tools/TerrainFormat/GeoPoint.cs`,
`tools/TerrainPreprocessor/CubeRegionFiles.cs`, `tools/MapCore/Pipeline.cs` (`AddCubeSteps`).

## The files: `--cube-region-files`

```
TerrainPreprocessor --cube-region-files --chunks LV95_CHUNKS --cube-out REGION
```

- Each stage keeps its maths. This step writes the stages' output into the cube region with every position also as
  `GeoPoint` (WGS84 latitude, longitude, ellipsoidal height), rigorously (`SwissGeodesy`). Each point goes at its own
  height (a summit's, a deck's, still water, a stand's ground), or the LV95 build's ground where the file has none.
  Every grid heading is also given from true north. The LV95 fields stay until D, since the game reads them until then.
- Formats: optional members, null and not written in the LV95 build's files, which are byte-identical.

| File | Earth members |
|---|---|
| `places.json` | `Place.Geo` |
| `pois.bin` | version 2 (written only when every record has one): each record's `Geo`, outlines' `GeoOutline` (lat, lon pairs at the POI's height); the decoder reads 1 and 2 |
| `landings.json` | `Landing.Geo` (still water), `LandingBerth.Geo` + `GeoHeading`, `PierRibbon.GeoPoints`, `Landing.GeoBollards` |
| `airports.json` | `Airport.Geo`, `AirportRunway.Geo1/Geo2`, `AirportStand.Geo` + `GeoHeading` |
| `ropeways.json` | `RopewayInfo.Geo0/Geo1` |
| `traffic_endpoints.tsv` (the test region) | four trailing columns `lat lon h true_heading` (the reader ignored extra columns before) |

- **Not here**:
  - **Wikidata's `atlas_facts.json`**: it carries no positions, only a match distance and an elevation.
  - **`horizon.bin`**: none is written for a cube region. Its far terrain is the pyramid.
  - **`manifest.json`**: the cube region has `cube_manifest.json`.
- **The check** runs at the end of every run. Each written file is read back and every Earth position is taken back to
  LV95 at its height, held to 2 cm (POIs to 5 cm: their v1 records keep LV95 to the decimetre). Each true heading is
  turned back to the grid, held to 0.001°. Counts must be equal file by file.

## Castles, venues and givers (after buildings, #1535)

- Written by their own stages (decided with the user: in the stages, exact on the solids; the committed nationwide
  files gain the Earth positions at their next full rebuild, on a machine with every canton's buildings):
  - **`--castles`** writes, beside `Castles.List.cs`'s `List`, a `Geo` array: per castle, latitude, longitude and
    ellipsoidal height of each point at the base (`MinY`) of the solid it is in.
  - **`--venues`** adds `lat lon h` columns after the name. The height is the base of the solid the venue is inside or
    snapped onto; in the open, the tiles' ground; off the built tiles, the Plateau's height, as `GeoInput` placed the
    OSM point, so it goes back to OSM's latitude and longitude.
  - **`--givers`** adds `lat lon h true_heading` columns. The height is the ground (the Plateau's off the tiles); the
    heading is in radians from true north.
  - The columns are written only when every row has them; the readers (at least 9 columns) read them when present.
- Checked on the D: region's buildings: 35 castles (35 `Geo` rows), 29,786 venues (inside a solid 2,661, median
  451 m ellipsoidal; snapped 191; open 368; off the tiles 26,566 at the Plateau's ~500 m), 317 givers (423-1,565 m).
