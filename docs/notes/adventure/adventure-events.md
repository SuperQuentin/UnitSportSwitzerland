# Adventure events: what a player did, raised by the system that checked it (#1223)

`src/Adventure/AdventureEvents.cs`, plain C#.

## Rule

- **Raise on the server only** (offline on the client playing its part), **after** the raising system
  has checked the act and written and touched its own section:
  `AdventureService.Instance?.Events.Raise(new PoiDiscovered(peer, key, id, kind, canton))`, where `key`
  is `Progress(peer).Key`.
- **A new event is a new record in the raising plan's own file**, deriving from
  `AdventureEvent(long Peer, string Key)`: the quest engine matches by type, nothing here changes.
  Already planned: `CantonMilestone`, `ChapterCompleted` (places), `StaminaRaised` (stamina),
  `EdelweissOffered` (rewards).
- Ids and kinds are strings owned by their plan (`PoiId`, `ChestId`, `PointId`, `"pass"`, `"UR"`), so
  this file depends on no other plan's enum. Cantons are the two-letter codes.
- No log line per event.

## The shared set

`PoiDiscovered`, `ViewpointSynced`, `CollectibleTaken`, `ChestOpened`, `TrialFinished`, `PhotoTaken`,
`TravelUnlocked`, `ItemObtained` (a reward or a chest's items, raised by `Grant`), `ItemDelivered`
(raised by `AdventureService.Deliver`), `Interacted` (raised by the interactable's own server method),
`QuestCompleted` (raised by the service, so quests chain).

## The bus

`AdventureEvents`: `Raise(e)` and `event Raised`, synchronous on the main thread. It drops an event
whose peer is not `Active` (a Battle Royale entrant; `Dropped` counts them). The service listens and
feeds the quest engine; nothing listens on clients (they get progress through `SectionSync`).

## How to check

`QuestEngineTests` (each step kind against every shared event; the bus drops an inactive peer's).
