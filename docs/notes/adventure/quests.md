# Quests: data in a C# catalog, steps that listen to events, rewards applied once (#1223)

`src/Adventure/Quests/`: `QuestDef.cs` (definitions, step kinds, rewards, sources), `QuestEngine.cs`
(the `quests` section and the rules), `QuestCatalog.cs` (the quests that ship, and the checks' own).
Plain C#, linked into the unit tests (`QuestEngineTests`, `QuestCatalogTests`).

## Rule

- **A new quest is a catalog entry**, never code in the systems it listens to: `Q(id, title, blurb,
  [steps], [rewards]) with { Canton, Requires, Start, Repeatable }`, the `Crafting/Recipes.All` idiom.
- **A new step kind is a `Step` record in its plan's own file**: `Matches(event)`, optionally `Amount`
  (an item step counts the items), `Distinct` (an id counted once: a POI found twice is one), `Target`
  (for the tracker), and `Plan` (`places`, `rewards`, `navigation`, `stamina`, or null when this
  service raises its events).
- **Quests are offered only when every step's plan runs** (`QuestEngine.Playable`; a plan calls
  `AdventureService.Provides("places")` when its system starts, **on the server and on clients**: the
  server refuses to start an unplayable quest, the client's Journal offers only playable ones). Until the other plans land, the five
  starter quests are in the catalog but not offered: the Journal says new quests come with the Atlas,
  travel points and chests.
- `Unlock(kind, arg)` rewards name a kind another plan registers (`RegisterReward`): `reveal`, `travel`,
  `stamina` (`QuestCatalog.UnlockKinds`, checked by the catalog test). An unregistered kind is logged,
  not applied.

## Steps

| Step | Advances on |
|---|---|
| `ReachStep(Area or Poi)` | the server's 2 Hz position check (only players whose current step is a reach, or who may start a quest on one), or `PoiDiscovered` of that POI |
| `DiscoverStep(Kind?, Canton?)` | `PoiDiscovered`, distinct POIs |
| `CollectStep(Kind?, Item?, Canton?)` | `CollectibleTaken` (distinct) / `ItemObtained` (counts items) |
| `DeliverStep(Item, target)` | `ItemDelivered` at that target (the hand-over, below) |
| `OpenChestStep(Tier?, PoiId?)` | `ChestOpened` (tier at least) |
| `TrialStep(TrialId, MaxSeconds?, Medal?)` | `TrialFinished` |
| `PhotoStep(TargetId)` | `PhotoTaken` |
| `InteractStep(TargetId)` | `Interacted` |
| `UnlockStep(PointKind?, PointId?)` | `TravelUnlocked`, distinct points |
| `FinishStep(QuestId)` | `QuestCompleted` |

Builders: `Reach`, `Photo`, `Deliver`, `Area(name, E, N, radius)` (LV95), `Poi(id)`.

**Places in quests are canonical POI ids** (`QuestCatalog.Places`: the curated Atlas cards' ids, checked by
`QuestCatalogTests`): the places service raises its events with canonical ids, never aliases. With places
running (#1224) a `Poi` reach step advances only on `PoiDiscovered` (`QuestEngine.PoisByDiscoveryOnly`): the
travel rule holds; `ResolvePoi` still locates it for the tracker. Uri passes is offered once places run; Top of
Zurich and Rigi wait for rewards (photos, chests), Gruyère for its requirement, Aletsch for navigation.

## Rules (`QuestEngine`, pure)

- Steps run in order; one event moves one step. At most 8 quests run at once; one is tracked (the first
  started; the next running one when it ends).
- `Start = OnEvent`: the quest starts by itself on its first step's event (or on reaching its first
  area) and counts it. Never offered in the log.
- `Requires`: done first. `Repeatable`: may start again once done.
- Completion is reported once: the quest leaves `Active` for `Done` (Unix time) in the same call, so the
  service applies its rewards once, in that frame: `Cash` to the bank **account** (`Bank.Credit`, not the
  pocket a knock-out empties), `Item` to the pack (`Granted`, what does not fit dropped at the feet),
  `Title` (earned list, the first one worn), `Unlock` through the plan's handler. Then
  `QuestCompleted` is raised.
- The `quests` section: `Active` (id -> step, count, started, distinct ids seen, seed), `Done`,
  `Tracked`, `Titles`, `Title`.

## Hand-overs (`Deliver`)

The pack is the client's, so the server checks where, not what: the client sends
`RequestDeliver(quest, step)` only with the item in its pack; the server checks the quest runs, the step
is that delivery and the peer's published position is within the target's radius + 5 m, answers
`DeliverOk`, and raises `ItemDelivered`; only then does the client take the items, as cash leaves the
pocket only when the bank answers. Server path for a bot: `AdventureService.Deliver(peer, quest, step)`.

## Sources

`IQuestSource { Id; For(ctx); Resolve(id) }`: `QuestCatalog` is the first. A generator (the Postkarte
errands, phase 3) rebuilds a quest from its id and `QuestState.Seed`; nothing else is saved.
`ProbeQuests(E, N)` is the checks' source (`--adventure-test`, `--adventurecheck`): an errand (reach A,
hand an apple over at B; CHF 25, a chocolate, a title) and a repeatable walk, 30 m from the spawn.
