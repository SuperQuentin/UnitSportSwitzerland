# Nakama: the trainer edition's meta backend (#1121)

- **What it is for**: accounts, race results, leaderboards, and later events (tournaments), clubs and matchmaking
  (`docs/plans/trainer-edition.md`). **The realtime ride stays on the Godot ENet server**: Nakama never runs the race,
  it only stores who rode which course and how fast.
- **Where**: `tools/nakama/`, which holds:
  - `docker-compose.yml`: Postgres 16 and `heroiclabs/nakama:3.41.0`, which runs `migrate up` before every start;
  - `local.yml`: settings without secrets;
  - `.env.example`;
  - `modules/index.js`;
  - `up.sh` and `check.sh`.
- **Run it**: `tools/nakama/up.sh` (with `up`, `down`, `logs` or `ps`).
  - The first `up` writes `tools/nakama/.env` with a random key for every `change-me`. The file is gitignored and
    is the only copy of the keys.
  - `up` waits until both containers are healthy.
  - `down` keeps the database volume. `docker compose down -v` deletes every account and record.
- **Ports** (#1205):
  - **7350** is the API and realtime socket. Docker publishes it on **127.0.0.1** only (`NAKAMA_BIND`, the compose
    default). On the server, Caddy serves it at **`https://unitsport.infrack.ch/nakama/`** (`handle_path /nakama/*`,
    the prefix stripped), as `/api/` goes to the layout service. Players, the website and game servers use that
    address, over the site's HTTPS.
  - **7351** is the admin console, bound to `127.0.0.1` only. On a server, reach it with
    `ssh -L 7351:127.0.0.1:7351`.
  - gRPC (7349) is not published.
  - A host without Caddy (`TILES=0`) still publishes 7350 on every interface (`NAKAMA_BIND=0.0.0.0`) and opens it in ufw.
  - `NAKAMA_PORT`, `NAKAMA_CONSOLE_PORT` and `NAKAMA_BIND` in `.env` move them.
- **Keys** (`.env`):
  - `NAKAMA_SERVER_KEY`: in the game client, for authentication (basic auth). It is not a secret from players.
  - `NAKAMA_HTTP_KEY`: **race servers only**, for server-to-server RPCs. Never ship it in a client build.
  - Console login.
  - `NAKAMA_ENCRYPTION_KEY`: session tokens. Changing it logs everyone out. The refresh and console signing keys
    are derived from it.
  - `POSTGRES_PASSWORD`: changing it after the first start locks Nakama out of the existing volume.
  - The secrets go in as command-line flags in the compose entrypoint, because Nakama's YAML cannot read the
    environment.
- **The module is plain JavaScript** (Nakama's JS runtime), not TypeScript, so there is no Node and no build step
  on the server.
  - Nakama looks registered functions up by name, so each one is a **top-level `function` declaration**. An arrow
    function or a function expression fails at load.
  - `healthcheck` returns `{ok, module}`.
  - `submit_result` takes `{course, playerKey, accountId?, name?, timeMs, avgWatts?, event?}` and returns
    `{leaderboard, rank, best}`. It is called as `POST /v2/rpc/submit_result?http_key=<key>&unwrap` with the raw
    JSON body.
  - **Names are never stored in a record** (#1359). With `accountId` (a signed-in rider, checked by the race server's
    `AccountGate`) the record is that account's; without, it is the PlayerKey fingerprint's user, whose display name
    holds the offline rider's plain name, one copy refreshed by each result. Records carry `account: true|false`. Each
    record also keeps `metadata.name`, the name it was set under: a backup shown only once its user is gone (a deleted
    account).
  - `scoreboard {course, limit?, cursor?}` reads a board with every name looked up now: the account's username, or
    the offline user's display name (a record from before #1359, without the flag, falls back to the name stored in
    it). **Read boards through it**, not `GET /v2/leaderboard`, whose record usernames are Nakama's copy from the write.
- **Forgotten passwords** (#1257): Nakama sends no mail, so the layout service (`net/house-layouts`, which has `SMTP_*`) does.
  - The module holds the token. `password_reset_issue {email}` and `password_reset_apply {token, password}` are
    **http key only** (a player's session gets 403). Issue returns `{token}` for an account with that email (banned
    ones excluded) and `{}` for none; a new request replaces the account's earlier token.
  - The token is 64 hex characters; only its SHA-256 sits in a system-owned storage object (collection `password_reset`),
    valid 30 minutes and spent by one use, even a failed one. Apply refuses a password outside 8 to 128 characters and
    sets it with `nk.linkEmail` on the account's own email (checked on Nakama 3.41: it replaces the password).
  - The service's `POST /api/password/forgot {email}` answers 200 whether or not the account exists, mails
    `<site>/reset.html#token=…` (the fragment never reaches a log), and waits a minute between two mails to one address,
    on top of the `login` rate limit. `POST /api/password/reset {token, password}` applies it. Both answer 503 without
    `NAKAMA_URL` and `NAKAMA_HTTP_KEY`; with no `SMTP_HOST` the link goes to the service's log.
  - The deploy writes both into `layouts.env` on `--setup`, reading the key from the host's Nakama `.env`. On a first
    deploy, run `--nakama`, then `--setup` again.
  - Asked from the site's sign-in dialog (**Forgot your password?**, `web-dashboard`), `reset.html`, and the game's
    Account page (`net/accounts`). `tools/nakama/check.sh` covers the RPCs.
- **Trust boundary**: a result comes only from a race server, which already checked the checkpoints and timed the
  finish on its clock (`RaceManager`).
  - `submit_result` refuses any call made with a player's session (`ctx.userId` set) with **403**. Invalid fields
    get **400**.
  - The `course:<id>` leaderboards are **authoritative** (only the server writes), **ascending** (lower time
    wins) and use the **best** operator (a slower ride never replaces a faster one).
  - Players read them with their own session through the `scoreboard` RPC.
  - Watts are still the rider's own word, as in Zwift.
- **Accounts**: a rider's Nakama user is created on their first result, with their **PlayerKey fingerprint as the
  custom id** (`nk.authenticateCustom`, 6 to 128 characters of `[A-Za-z0-9_-]`).
  - A player's own session comes from their own sign-in (`net/accounts`, #1123), never from the public
    fingerprint.
- **Check**: `tools/nakama/check.sh` prints `RESULT: PASS|FAIL`.
  - It runs on its own compose project (`-p unitsport-check`, ports 17350 and 17351, random keys) and deletes it
    afterwards, so it never touches the stack `up.sh` runs.
  - It covers: the healthcheck; three results, where the best of 60, 55 and 70 s must stand at 55 s; a bad course
    refused with 400; a device-authenticated player reading the board, then refused with 403 on `submit_result`.
  - It is not in `tools/test.sh`, which has no Docker.
- **Backup**: run
  `docker compose -p unitsport-nakama exec postgres pg_dump -U postgres nakama > nakama.sql` in `tools/nakama/`.
- **Upgrade**: bump the image tag in `docker-compose.yml`, then run `up.sh`. Migrations run at start. Read the
  Nakama release notes for breaking runtime API changes first.
- **On the Linux host**: `tools/deploy-linux.sh --nakama`, or `NAKAMA=1` for every full deploy
  (`general/linux-deploy`). The host's `.env` is made there once and never overwritten.
- **Not yet**:
  - the C# client (`NakamaClient` NuGet) and the race server's `NakamaRaceResults`;
  - events as tournaments.
  - These are deliverables 2 to 4 of the plan.
