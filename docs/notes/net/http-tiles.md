# Tiles over HTTP: a static mirror beside the game server (#651)

- **Why:** tiles are static files (~112 GB, ~246k). Over ENet they go 24 KB at a time through the game
  process, capped at 3 MB/s per client. A static HTTP server sends them with sendfile, gzip copies and
  HTTP/2, with no work in the game process. Rust was considered and not used: a custom server only pays
  off when tiles are built per request.
- **Server:** `--tiles-url <url>` (or `UNITSPORT_TILES_URL`) sets `ChunkStreamer.TilesUrl`. A client
  asks for it as `AssetKind.HttpBase` through the ordinary `RequestAsset`. No new RPC (that would
  renumber the node's RPCs) and no protocol bump: an older server doesn't know kind 13 and answers
  "missing", and an older client never asks.
- **Client:**
  - `ClientTerrainSync.SyncHttpAsync` runs before the manifest. It fetches the URL, then
    `HttpAssetSource.ProbeAsync` sends a HEAD for `manifest.json`. Only a mirror that answers becomes
    `ChunkStreamer.Http`.
  - From then on, `ChunkStreamer.FetchAsync` tries the mirror first for every `AssetStream.ServedOverHttp`
    kind. That is all tile files plus `places.json` and `horizon.bin`. The manifest, landings and CDs
    stay on ENet because the server may serve an override, or another directory.
  - **A 404 is final** ("this tile has no .holes"). That's safe only because the probe proved the URL
    points at the right directory.
  - **Any other failure** (refused, timeout, 5xx) falls through to ENet for that request. 8 in a row
    drop the mirror for the session, logged once. Bytes count on both paths (`SessionBytes`).
- **`HttpAssetSource`:** one shared `System.Net.Http.HttpClient` (Godot has its own `HttpClient`, hence the
  alias). It requests HTTP/2, falling back to 1.1 for plain http, and inflates gzip and brotli. The
  `NetworkChunkSource` limit of 6 requests in flight still applies.
- **Measured** (Oct 2026, loopback, fresh client, spawn, default settings):
  - Over HTTP, 310 MB (2,235 files) were in the cache about 20 s after joining.
  - Over ENet only, the same files took about 120 s.
  - Caddy killed 20 s in: the client logged the drop after 8 failures and finished over ENet.
- **Faster delivery exposed a Windows race in `WriteCache`.** When two fetches of the same file finish
  together, `File.Move` onto a file another thread is reading throws "Access denied". The target
  already holds the same bytes, so that case now counts as written: 6 warnings a run before, 0 after.
- **Caddy 2.10.2 answers `206` with the whole body** when it sends a precompressed `.gz`. `HttpClient`
  accepts it, so nothing to do; worth knowing before a CDN goes in front.
- **Deploy** (`general/linux-deploy`): Caddy runs on the same host, from `tools/deploy/Caddyfile`. The
  chunk step runs `tools/deploy/gzip-tiles.sh` on the host: a `.terr` goes from 2 MB to 0.4 MB, about
  +25% disk in total.
- **Local test:** a Caddy binary with the rendered template on `http://127.0.0.1:<port>`, plus
  `--tiles-url http://127.0.0.1:<port>/tiles/` on a loopback server. A client with empty `--chunks` and
  a scratch `APPDATA` should log `[stream] tiles from ... (HTTP)`. A `log` block in the site gives the
  request count.
